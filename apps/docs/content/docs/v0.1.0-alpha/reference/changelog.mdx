`v0.1.0-alpha` is the first cut. There is no previous version to diff against; this is what the implementation will land with on day one.

## Focus

Local compiler and runtime proof. The goal is to show that a developer-supplied control plane can produce validated LWIR and execute it durably enough for local development.

## New Authoring Surface

- `createLittleWorkflow(definition)` — the front door, accepts the minimal definition shape (id, description, input schema, output schema, models, tools).
- `runWorkflow({ world, workflows, input, timeout })` — execute a workflow against a world.
- `localWorld({ dataDir })` — the zero-service local development backend.
- Default `workflowHarness` support — planner, orchestrator, worker, and fixer roles run through the Harness contract; developers can swap in a custom harness per role.

## New Runtime

- `OrchestrationRequest` schema and normalization from the minimal `createLittleWorkflow()`.
- Canonical LWIR JSON with hashing and Ajv validation against the supported JSON Schema subset.
- Harness-backed planner path with a bounded validation and repair loop.
- Initial step types: `ai.generate`, `tool.call`, constrained local `code.run`, and bounded `parallel` coordination.
- Simple capability allowlist (no full firewall yet).
- Local World SQLite/WAL event store, artifact manifests/blobs, local run locks, retry of failed steps, and replay from event history without re-calling completed model or tool steps.

## New CLI

- `little validate <file>`
- `little run <workflow.json> --input <file>`
- `little events <run-id>`
- `little replay <run-id>`

Planner-backed `little orchestrate` is reserved for the post-alpha CLI harness-loading contract. Alpha orchestration is available through the SDK `runWorkflow()` harness path.

## New Demos

- A kill-and-resume demo that proves a local run survives a process kill and resumes from persisted state without re-calling completed steps.

## New Verification Contract

The alpha implementation needs Vitest coverage for:

- schema normalization from JSON Schema descriptors, Zod v4 schemas, and AI SDK output-mode specs
- canonical JSON hashing and hash stability
- Ajv LWIR validation and compact validation errors
- planner repair loop with mocked AI SDK calls
- `workflowHarness` AI SDK output-mode mapping and fallback detection
- event append and replay ordering
- result envelope persistence and artifact refs
- automatic retry without re-calling completed steps
- bounded parallel branch fan-in order and failure modes
- Local World kill-and-resume behavior

## Milestone: alpha-grilling-gaps-closed

This milestone closes the implementation gaps identified during the alpha grilling session. It comprises 38 commits across four sequential phases.

### Stream A — Code follow-ups from existing ADRs

Four independent ADR code follow-ups shipped first, each with its own test coverage:

**Tool registry.** `WorkflowDefinition.globalTools` changed from an inline `Record<string, AiSdkTool>` to a `readonly string[]` of names. A new `createToolRegistry()` function provides the process-level registry where developers register tool descriptors and handlers once. The compiler reads descriptors from the registry to build the `WorkflowVersion` lock; the runtime reads handlers at step lease. Re-registering a name with a different descriptor throws. This is a breaking API change within the alpha phase.

**Concurrency cap.** `localWorld()` now accepts `maxConcurrentSteps?: number`. A global semaphore in the scheduler limits total in-flight step attempts across all parallel groups and serial steps in a run, preventing compute saturation on developer machines. Default is `undefined` (no cap). Documentation recommends `os.availableParallelism()` as a starting value for compute-heavy workflows.

**Artifact output store.** Inline `output` in `StepCompleted` events is now omitted when the serialized output exceeds 256 KB. The `outputRef` artifact is always written and is the canonical source of truth. A `sensitive: true` field is accepted and validated on step metadata but not yet honored by the runtime — it is reserved for a future release that will suppress inline output regardless of size.

**Drift policy.** Tool `outputSchema` is now included in the capability snapshot hash and in the drift check at step lease time. Previously only `description` and `inputSchema` were hashed. `RunFailedError` for `capability_drift` now includes a one-line re-run hint in its message.

### Layer A — Decision-driven LWIR

Layer A makes AI-generated workflows expressive enough for real review/revise patterns by adding bounded control flow inside a single workflow execution.

**Decision step type.** A new `decision` LWIR step type evaluates an ordered `cases[]` list of `when` expressions and routes to the first matching `to` target, falling back to `with.default`. The `to` sentinel `"end"` terminates the current scope (a parallel branch or the top-level workflow). The `StepCompleted` payload for a decision step is `{ chosen: "<targetId>" }`, making every routing decision auditable. Decision steps are excluded from fan-in output.

**`maxVisits` and back-edges.** Every LWIR step now accepts an optional `maxVisits` integer (range `[1, 100]`, default `1`). When `maxVisits > 1`, a `decision` step may route back to that step, creating an in-workflow loop. The LWIR validator runs Tarjan's SCC algorithm over the union of `needs` edges and decision-step transition edges; a cycle is valid only if it contains at least one `decision` step and every step on the cycle has `maxVisits ≥ 2`. At runtime, exceeding `maxVisits` fails the run with `RunFailedError { causeCode: "max_visits_exceeded", failedStepPath }`.

**Visit-indexed step paths and replay.** Multi-visit steps gain a `.visit[N]` suffix (0-indexed) in their step path. The durability unit becomes `(stepPath, visitIndex)` — a committed `StepCompleted` for `worker.visit[0]` is immutable; `worker.visit[1]` is a separate execution. Replay reconstructs visit counts from the event log. Single-visit (DAG) step paths are unchanged.

**Expression accessors.** Two new accessors on step references: `{{ steps.X.lastOutput }}` (output of the most recent committed visit) and `{{ steps.X.allVisits }}` (ordered array of all committed visit outputs). Referencing `{{ steps.X.output }}` on a step with `maxVisits > 1` is a validation error (`lwir.output_ambiguous_for_multi_visit`) — the planner must be explicit.

**Branch final output and `fanIn.outputStep`.** When a parallel branch terminates via a decision step, its fan-in contribution is the `lastOutput` of the most recently committed non-decision step, or the `lastOutput` of a specific step if the parallel group declares `fanIn.outputStep: "<stepId>"`.

### Layer B — Planner as outer loop

Layer B adds bounded supervision across multiple workflow runs, letting the planner review its own output and iterate.

**Planner `supervise` hook.** `WorkflowDefinition.planner` gains an optional `supervise?(state: SuperviseOuterLoopState): Promise<SuperviseDecision>` hook. When absent, every workflow stays single-cycle. When present and `runWorkflow` is called with `maxOuterCycles > 1`, the outer loop is engaged. `SuperviseDecision` is either `{ kind: "done", finalOutput }` (terminate) or `{ kind: "continue", promptNote? }` (start next cycle, optionally appending a note to the next request's system message).

**Outer-loop scheduler.** After each cycle's `RunCompleted` or `RunFailed`, the runtime calls `supervise` and dispatches on the result. Cycles share an `outerLoopId` (a UUID). Each cycle is a full compile-and-execute with its own `runId` and `WorkflowVersion`. The `OrchestrationRequest` carries `outerLoop.cycleNumber`, `outerLoop.maxCycles`, `outerLoop.isFinalCycle`, and `outerLoop.priorCycles`. If `supervise` returns `continue` on the final cycle, `runWorkflow` throws `RunFailedError { causeCode: "outer_loop_exhausted", outerLoopId, lastCycleOutput }`.

**Durability and replay.** Each cycle appends an `OuterLoopCycleCompleted` event to its event log and updates the `outer-loops/{outerLoopId}.json` manifest transactionally. A `pendingCycleRunId` field in the manifest is written before a cycle starts and cleared after its `OuterLoopCycleCompleted` event is written; on resume after a mid-cycle crash, the scheduler reuses that `runId` so Layer A replay can continue from the last committed step. Kill-between-cycles recovery reads the manifest on resume and re-enters the scheduler at the correct cycle.

**`RunStarted.payload.outerLoopId`.** The `RunStarted` event for each cycle carries the shared `outerLoopId`, making the full outer-loop session traceable from any cycle's event log.

### Demo — `demo-real-planner`

A new `apps/demo-real-planner` application was scaffolded and built out with two runnable variants. The single-cycle variant demonstrates the candidate-review workflow using a real planner model against a fixture dataset, proving the Layer A loop end-to-end. The supervisor variant adds `maxOuterCycles: 3`; the planner reviews the first run's output, decides it was inconclusive, and generates a second cycle with a tighter prompt — demonstrating the Layer B supervisor pattern. The `CapabilityManifest` was updated to advertise the `decision` step type to the planner.
