---
title: Planner Lifecycle
description: How a normalized OrchestrationRequest becomes an immutable WorkflowVersion.
---

The planner is a model-driven compiler, not a runtime executor. Its job is to turn a normalized `OrchestrationRequest` into validated LWIR that the runtime can execute durably.

## The Four Stages

```txt
draft -> validate -> repair -> register
```

Each stage is deterministic at its boundary, even when the model itself is not. The validation/repair loop is bounded; if it does not converge, the planner fails the request rather than register a workflow nobody can trust.

## What The Planner Sees

The planner reads only the safe surface of the request:

- the goal and input/output schemas
- model slot metadata (role, capabilities, quality tier, cost class, allowed destinations)
- tool descriptions and input schemas for tools the developer passed in `model().tools` or `globalTools`
- skill catalog entries and policy snapshot
- approval rules, budget caps, and data classes

It never sees:

- secrets, environment variables, or signed credentials
- raw tool implementations or executable function bodies
- arbitrary stored artifacts unless policy explicitly grants planner access

Planner-visible is not planner-callable. The planner can reference a capability in a draft LWIR document, but the runtime is what decides whether the capability is invoked.

## Draft

The planner produces a draft LWIR document. The draft references model slot IDs and capability refs by ID, populates step schemas, and includes any reducer or fan-out structure the goal requires.

The model used for drafting is itself a governed slot — usually `role: "planner"` with `qualityTier: "reasoning"`. Default settings, allowed overrides, cost caps, and call caps from the slot bound the draft step.

## Validate

Deterministic validators run against the draft:

- canonical JSON shape and JSON Schema subset
- expression language whitelist (no arbitrary JavaScript, no I/O, no dynamic imports)
- capability references resolve to manifest entries
- model slot references resolve and satisfy step requirements
- policy snapshot conformance (budget caps, approval rules, data classes, allowed destinations)
- schema compatibility between steps and pipeline boundaries

Validation outputs structured findings, not free text, so the next stage has something to act on.

## Repair

When validation fails, the planner gets the findings back and produces a revised draft. The repair loop is bounded by:

- maximum repair attempts (configurable, defaults conservative)
- planner cost cap per request
- planner call cap per request

If the loop exhausts its budget without a clean draft, the request fails. Failure is preferable to registering a workflow that contradicts its own policy snapshot.

For requests configured for human review, an exhausted repair loop pauses for an operator decision instead of failing outright.

## Register

A clean draft is registered as an immutable WorkflowVersion. Registration captures:

- canonical JSON hash of the LWIR document
- capability manifest hash (which tools, which versions, which descriptions)
- policy version hash
- skill and plugin lock snapshots (content-addressed)
- compiled expression plan
- validation result and cost/risk estimate

After registration the WorkflowVersion is read-only. Runs reference it by hash. If the underlying model, tool, skill, or plugin surface drifts, the worker detects it at lease time and either fails the step or pauses the run for review.

## When The Planner Re-Runs

Almost never inside a run.

- A `Run` executes one registered WorkflowVersion. The planner does not re-plan mid-run.
- `Retry` reuses the same WorkflowVersion and re-executes the failed step.
- `Replay` reuses the same WorkflowVersion and rebuilds state from the event log without calling models or tools.
- `Fork` is the one place the planner can re-engage. A fork can change inputs, model slot mapping, prompts, policy, or output schema. The result is a new WorkflowVersion with provenance back to the original.

This is the trade. Determinism and replayability come from freezing the plan at registration. Adaptation comes from forking, not from quietly mutating a running workflow.
