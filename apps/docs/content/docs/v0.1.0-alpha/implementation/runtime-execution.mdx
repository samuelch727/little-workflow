`runtime.ts` drives the execution of a locked `WorkflowVersion`. The core loop is unchanged: schedule steps in dependency order, execute each one, write every result boundary to Local World. The implementation of each step has changed fundamentally — all step types now go through the **worker harness** instead of separate `RuntimeAiAdapter` / `RuntimeCodeRunner` / tool-dispatch paths.

## Two Entry Points

| Function | When to use |
|---|---|
| `runWorkflow(options)` | Full path: planner harness session drafts LWIR, then worker harness sessions execute steps. This is what authors use. |
| `executeWorkflowVersion(options)` | Post-compile path. Takes an already-locked `WorkflowVersion`. CLI uses this; tests use it for surgical scenarios. |

`runWorkflow()` is a thin wrapper. After the planner session completes and LWIR is locked, it appends planner events + `WorkflowVersionRegistered` + `RunStarted`, then hands off to `executeWorkflowVersionUnlocked()`.

## In-Process Fence

Both entry points wrap execution in `withRunExecutionFence(world, runId, fn)`:

- An in-process `Set<string>` rejects concurrent calls for the same `(dataDir, runId)`.
- A filesystem lock under `<dataDir>/locks/<sha256(runId)>` rejects concurrent calls from other processes.
- The lock owner file records `pid` and an opaque `token` so stale locks can be reclaimed.

This is what makes kill-and-resume safe.

## Step Scheduling

The LWIR scheduler is unchanged from before this milestone. It schedules steps in dependency order, handles `decision` routing, and manages `parallel` branches concurrently.

**Decision-target exclusion (P1.2 fix):** decision targets are excluded from the runnable set until their decision step routes to them. A decision that commits `{ chosen: "targetId" }` unlocks exactly one target.

**Non-parallel in-flight resume (P1.4 fix):** top-level non-parallel steps that were in-flight at kill time resume on the same `attemptId` rather than raising `RuntimeIntegrityError`.

```ts
const completed = completedStepIds(lwir.steps, state);
const remaining = new Set(lwir.steps.map((s) => s.id).filter((id) => !completed.has(id)));
const decisionTargetIds = new Set(collectDecisionTargetIds(lwir.steps));

while (remaining.size > 0) {
  const nextStep = lwir.steps.find((step) =>
    remaining.has(step.id) &&
    !decisionTargetIds.has(step.id) &&
    (step.needs ?? []).every((need) => completed.has(need)),
  );
  if (nextStep === undefined) {
    throw new Error("No runnable LWIR step found; dependencies incomplete or cyclic.");
  }
  await dispatchStepToWorkerHarness(/* ... */);
  completed.add(nextStep.id);
  remaining.delete(nextStep.id);
}
```

## Harness Session Lifecycle Per Step

For every LWIR step, the runtime:

1. Constructs a `WorkerManifest` (harness id, workflow definition hash, workflow version id, step config hash, model slot, skills, tools).
2. Calls `worker.harness.run({ kind: "execute_step", step, stepInput, stepContext }, ctx)`.
3. The harness emits `harness.session.started` (carrying the manifest + manifest hash) before doing any work.
4. The harness does its work (agent loop for `ai.generate`; direct execute for `code.run` / `tool.call` / `decision`).
5. The harness emits `harness.session.completed` (with output + usage) or `harness.session.failed`.
6. The runtime validates output against the step's output schema, writes the artifact, appends `StepCompleted` or `StepFailed`.

`harness.session.started` carries the `WorkerManifest`. On resume, the manifest is recomputed and compared; a mismatch raises `CapabilityDriftError` (applied at the harness session level). See [Identity + Manifests](/docs/v0.1.0-alpha/implementation/identity-manifests).

## Worker Dispatch by Step Type

The worker harness (`workflowHarness` or custom) dispatches internally by step type:

| `step.uses` | Worker behavior | Model in loop? |
|---|---|---|
| `ai.generate` | Agent loop via AI SDK `streamText` / `generateText` — model + tools + bash | Yes |
| `code.run` | Direct JS execution in Node child process; `{input, tools}` proxy provided | No |
| `tool.call` | Direct invocation of the named tool from `ctx.tools` | No |
| `decision` | Pure expression evaluation against step context | No |
| `parallel` | Orchestrated by the LWIR scheduler, not the harness | — |

### `ai.generate` steps — agent loop

For AI steps, the worker harness runs an agent loop:

1. Assembles system prompt: dev-supplied worker system + SDK addendum + skill frontmatter list + memory/scratch mount descriptions.
2. Passes `ctx.tools` (step's `with.tools` allowlist subset) + bash to the agent.
3. Per turn: emits `harness.model.called` → invokes model → emits `harness.model.responded`.
4. Per tool call by the model: emits `harness.tool_call.started(caller: "model")` → invokes tool → emits `harness.tool_call.succeeded, harness.tool_call.failed`.
5. If the model uses bash JavaScript and Runtime Tool Bridge is enabled, each `tools.x(args)` call emits `harness.tool_call.*(caller: "runtime")` and uses the same tool allowlist, spooling, and replay machinery.
6. Continues until the model produces a terminal output matching the step's output contract.

### `code.run` steps — direct execute with tools proxy

For code steps, no model is invoked. The harness:

1. Emits `harness.session.started` + `harness.execute_step.started`.
2. Injects a `tools` proxy into the JS function: `async ({ input, tools }) => output`.
3. Each `tools.x(args)` call from within the code body emits `harness.tool_call.started(caller: "code")` → invokes the tool → emits `harness.tool_call.succeeded, harness.tool_call.failed`.
4. Emits `harness.execute_step.succeeded` + `harness.session.completed`.

The model never sees tool results from `code.run` — token savings vs. a model-in-the-loop approach.

### Fixer — `fix_step` harness session

If a `code.run` step fails AND the step declares `onFailure.fixer`, the runtime spawns a **Fixer harness session**:

```ts
const fixResult = await worker.harness.run({
  kind: "fix_step",
  step,
  stepInput,
  originalAttemptError: errorEnvelope,
  priorFixAttempts: 0,
}, ctx);
```

The fixer is a full agent loop. It gets the failed code body, the error, the output schema, bash, and scratch. It iterates: edit code → run in scratch → inspect output → repeat. On success, `harness.session.completed` carries `fixedSource`. The fixed source is used for this run only — LWIR stays immutable. Persistent fixes go through memory: the fixer's system prompt encourages writing a lesson to `/mnt/memory/workflow/lessons-learned.md` for future planners.

The fixer task kind is `fix_step` — it maps to `HarnessRole: "fixer"` in the session started event.

See [Fixer](/docs/v0.1.0-alpha/implementation/fixer) for the full fixer spec.

## Per-Step Events

For each step, the runtime appends LWIR-level events alongside the harness session events:

1. `StepScheduled`
2. `StepAttemptStarted`
3. *(harness session events: `harness.session.started`, model/tool events, `harness.session.completed`)*
4. `StepOutputValidated`
5. `ArtifactCreated`
6. `StepCompleted` — durable boundary; inline output + `outputRef`

If the harness session fails:

1. `StepFailed` — with `error: { name, message, causeCode, retriable }`.
2. If retriable and `attempt < maxAttempts`: loop back to `StepAttemptStarted`.
3. If fixer declared and code.run: spawn fixer session before deciding terminal.

Terminal causes (`cancelled`, `timeout`, `capability_drift`, `runtime_config_error`, `step_schema_error`) skip retry.

## Input Resolution

`resolveStepInput()` builds the `input` value the harness receives. Unchanged from prior alpha:

1. `step.input` if present — resolved through `resolveExpressionValue()` against `(input, item, steps, workflow)`.
2. Otherwise an empty object.

## Capability Drift Checks

Before dispatching each step, the runtime:

1. Recomputes the `WorkerManifest` for this step.
2. Reads the `harness.session.started` event for this step (if a prior attempt committed one).
3. Compares `manifestHash`. Mismatch → `CapabilityDriftError(causeCode: "capability_drift")`.

For `ai.generate` steps: model slot id changing is drift. For `code.run` steps: harness id or step config hash changing is drift. This replaces the prior per-field `modelIdentityHash` + tool descriptor checks with a single manifest hash comparison.

## Outer-Loop Scheduler

The outer-loop scheduler in `outer-loop.ts` is unchanged. It wraps the per-cycle compile-and-execute loop:

1. Reads or creates the outer-loop manifest at `<dataDir>/outer-loops/{outerLoopId}.json`.
2. For each cycle: writes `pendingCycleRunId`, runs `runWorkflow`, appends `OuterLoopCycleCompleted`.
3. Calls the planner's `supervise()` method to get `{ kind: "done" | "continue" }`.
4. On `continue`, the next cycle's planner harness session receives `outerLoopContextHash` in its manifest (hash of prior cycles).

## Run Finalization

After the LWIR loop exits cleanly:

1. Resolves the final step (last step whose output matches the workflow's output schema).
2. Reads the final step's `outputRef` and rehydrates the payload.
3. Validates against the workflow's `outputSchema`.
4. Appends `RunCompleted` with `output`, `outputRef`, `terminalStepPath`.

Non-recoverable errors append `RunFailed` with a structured error envelope and `causeCode`.

## Resume Semantics

When `executeWorkflowVersionUnlocked()` starts with an existing event log:

1. Materializes run state via `materializeRunStateFromEvents()`.
2. Verifies persisted `RunStarted.input` matches `options.input`.
3. Verifies persisted `workflowVersionId` / `workflowVersionHash` match the supplied lock.
4. For each completed step: verifies the artifact still exists with the right sha256.
5. Skips steps whose `StepCompleted` events are committed.
6. For steps whose harness session started but did not complete: checks harness-level events — completed model/tool calls fast-forward from the event cache; only the in-flight call re-executes. Runtime Tool Bridge calls are replayed with `caller: "runtime"` and a scope tied to the parent bash tool call, so identical bridged calls in different bash commands do not collide.

This is the two-level durability model: LWIR per-step memoization composed with harness per-model-call + per-tool-call memoization. See [Replay](/docs/v0.1.0-alpha/implementation/replay) for a full treatment.

## Cancellation And Timeout

- `options.signal` and `options.timeout` merge into a single `CancellationController`.
- Every harness context receives `ctx.abortSignal`. The harness honors it: in-flight model calls are allowed to complete (best effort); in-flight tool calls are signaled; `HarnessCancelled` propagates up.
- The runtime writes `RunFailed(causeCode: "cancelled" | "timeout")`.

## Idempotency Guarantees

- Same `runId` + same input → returns persisted result or replays persisted `RunFailedError`.
- `RunCompleted` is final: the terminal step's `outputRef` is asserted equal to the run's `outputRef`. Mismatch raises `RuntimeIntegrityError`.
- The fence prevents concurrent live processes from racing the same run.
