---
title: Run A Workflow
description: How to execute a workflow definition or pipeline against a world, with options, return shape, errors, and streaming.
---

There are two entry points for execution.

- [`runWorkflow(options)`](#one-shot-run) — one-shot. Spins up a runtime, executes one run, returns the result. Fine for scripts, tests, and the kill-and-resume demo.
- [`createRuntime(options)`](#shared-runtime) — long-lived. Returns a runtime you can call `runtime.run(...)` on many times. Use this when one process serves many runs.

Both accept the same world adapter and produce the same artifacts and events.

## One-Shot Run

```ts
import {
  createLittleWorkflow,
  localWorld,
  runWorkflow,
} from 'little-workflow';

const result = await runWorkflow({
  world: localWorld({ dataDir: '.little-workflow' }),
  workflows: summarizeTicket,
  input: {
    ticketId: 'TCK-123',
    transcript: 'Customer reports intermittent billing export failures...',
  },
  timeout: '10m',
});

console.log(result.runId);
console.log(result.output);
```

`runWorkflow` returns a promise that resolves when the run reaches `RunCompleted`, or rejects on `RunFailed`. Internally it provisions a one-shot runtime, registers the WorkflowVersion if it isn't already, dispatches the first step, and waits.

## Options

```ts
type RunWorkflowOptions = {
  world: World;
  workflows: WorkflowDefinition | WorkflowPipeline;
  input: unknown;
  timeout?: string | number;
  signal?: AbortSignal;
  onEvent?: (event: RunEvent) => void;
  metadata?: Record<string, unknown>;
};
```

- **`world`** — the runtime backend. Use `localWorld()` for development; production worlds (Postgres + Redis + S3) arrive in v0.1.0.
- **`workflows`** — either a single `WorkflowDefinition` from `createLittleWorkflow()` or a `WorkflowPipeline` from `chainWorkflows()`.
- **`input`** — validated against the workflow's `inputSchema` before the run starts. A mismatch throws before any model is called.
- **`timeout`** — wall-clock cap. Accepts a duration string (`'10m'`, `'2h'`) or milliseconds. The run is cancelled and marked `RunFailed` if it elapses.
- **`signal`** — an `AbortSignal` for external cancellation. Same outcome as `timeout` but on demand.
- **`onEvent`** — optional callback fired for every event the run emits. The event log is durable regardless; this is a convenience for live observation.
- **`metadata`** — arbitrary key-value pairs attached to the run record. Useful for tagging runs by tenant, user, request ID.

## Return Shape

```ts
type RunResult<T = unknown> = {
  runId: string;
  workflowVersionId: string;
  status: 'completed' | 'failed';
  output: T;
  usage: {
    inputTokens: number;
    outputTokens: number;
    costUsd: number;
  };
  events: EventRef[];
  artifacts: ArtifactRef[];
};
```

`output` is typed by the workflow's output schema. `events` and `artifacts` are pointer arrays — the actual payloads live in the world's event log and artifact store and can be inspected with the CLI or the inspect APIs.

## Shared Runtime

When one process handles many runs, use `createRuntime` to share connections, worker pools, and governors across runs:

```ts
import { createRuntime } from 'little-workflow';

const runtime = createRuntime({
  world: localWorld({ dataDir: '.little-workflow' }),
  plugins: [],
  skills: [],
});

const result = await runtime.run({
  workflows: summarizeTicket,
  input: { /* ... */ },
  timeout: '10m',
});

await runtime.shutdown();
```

The runtime accepts the same per-run options as `runWorkflow`, minus `world` (which is set on the runtime itself).

## Errors

Both entry points reject the promise on `RunFailed`. The rejection carries the structured failure:

```ts
try {
  await runWorkflow({ /* ... */ });
} catch (err) {
  if (err.name === 'RunFailedError') {
    console.error(err.runId, err.failedStepPath, err.cause);
  } else {
    throw err;
  }
}
```

Common causes:

- **`InputSchemaError`** — input did not match the workflow's input schema. Thrown before the run starts; no run record is created.
- **`ValidationError`** — the planner could not produce a valid LWIR document within its repair budget.
- **`FatalStepError`** — a step failed in a way the runtime cannot retry (e.g. `capability_drift`, schema mismatch, policy denial).
- **`BudgetExhaustedError`** — the run hit its budget cap before completion.
- **`TimeoutError`** — the run exceeded `timeout`.

Recoverable step failures (transient network, rate limits) are retried automatically and never bubble up here.

## Cancellation

Cancellation always produces a `RunFailed` with `cause: 'cancelled'`. The runtime stops scheduling new steps, lets in-flight step attempts complete or be killed by their own timeout, and finalizes the run record.

```ts
const controller = new AbortController();
setTimeout(() => controller.abort(), 5_000);

await runWorkflow({
  /* ... */
  signal: controller.signal,
});
```

## Streaming

For workflows that emit token streams, subscribe before awaiting:

```ts
const handle = runtime.runStreaming({
  workflows: summarizeTicket,
  input,
});

for await (const part of handle.stream) {
  // part is an AI SDK stream chunk replayed from the durable event log
  process.stdout.write(part.text ?? '');
}

const result = await handle.result;
```

Stream parts are persisted to the event log as they arrive, so a reconnecting client gets the same parts in the same order — there is no dependency on `useChat` resumable streams. See [Durability](/docs/v0.1.0/run-inspect/durability) for the replay story.

## Replay, Retry, Fork

A `runWorkflow` call always starts a fresh run. To re-execute history, repair a failed step, or branch on changed input, use the CLI or the inspect APIs:

```bash
little replay run_123
little retry run_123 --from review-candidates.extract-profile
little fork run_123 --patch patch.json
```

See [Inspect Runs](/docs/v0.1.0/run-inspect/inspect-runs) and [Durability](/docs/v0.1.0/run-inspect/durability) for the semantics.
