---
title: Execution Tiers
description: Classify shell scripts before they run, and escalate the commands just-bash cannot run to a real sandbox.
---

Every built-in sandbox runs **Tier-0**: just-bash, bash emulated in
JavaScript over the session's virtual filesystem. Tier-0 covers file and text work
(`ls`, `rg`, `jq`, `sqlite3`, optional Python and JavaScript), but it has no git,
containers, compilers, package managers, or real network clients. Little Harness
ships two opt-in pieces for those commands:

- **Command classification** — `classifyCommand`, `detectEmulationGap`, and the
  versioned `tier0CapabilityMatrix()` decide whether a script can run on Tier-0.
- **Tiered execution** — `tieredSandbox({ nextTier })` is a sandbox factory
  that runs Tier-0 and switches to a higher tier
  you provide when a command needs it.

Nothing here is on by default. `localHost()`'s default `"auto"` mode chooses
*where* Tier-0 runs (in-process or the subprocess sandbox); tiers decide what
happens to a command Tier-0 cannot run at all.

## Classify Before Running

`classifyCommand(script, options?)` reads the script's AST and returns a decision
**without executing anything**:

```ts
import { classifyCommand } from "@little-stack/harness/sandbox";

classifyCommand("rm -rf build && cargo build");
// {
//   decision: "escalate",
//   reasons: [
//     { kind: "needs-real-exec", command: "cargo", reason: "build-toolchain" },
//     { kind: "tier0-supported", commands: ["rm"] },
//   ],
// }
```

| Decision | Meaning |
|---|---|
| `"run"` | Every command the script names is emulated at the given `runtime` settings. |
| `"escalate"` | The script is well-formed but needs a tier just-bash cannot provide. Not an error. |
| `"deny"` | `policy.denyCommands` forbids it. Escalating would not help. |

Deciding first is the point. Run on Tier-0, the script above deletes `build`
and only then fails `cargo` with exit 127; re-running it on a real tier repeats
the destructive prefix. Classification escalates before the first side effect.

Reason kinds are `tier0-supported`, `empty-script`, `unknown-command`,
`needs-real-exec` (with a reason such as `version-control`, `containers`,
`build-toolchain`, `package-manager`, or `network-client`), `capability-disabled`,
`policy-blocked`, `dynamic-command`, `opaque-script`, `parse-failed`, and
`classifier-unavailable`. A command just-bash *could* run but whose toggle is off
(`curl` without `runtime.network`, `python3` with `runtime.python: false`) is
`capability-disabled` and escalates — a tier with the capability runs it.

Options: `runtime` (the toggles the script would run under), `policy`
(`{ denyCommands, rule? }`), and `matrix` (pin a capability-matrix version).

Classification cannot see inside `./build.sh`, a command passed to a runner
(`xargs cargo build`, `timeout 5 docker ps`), or which flags an emulated command
implements. `detectEmulationGap(result)` is the back-stop: given a finished
Tier-0 result, it returns `{ kind: "emulation-gap", signal, command, option? }`
when stderr shows just-bash's own `command not found` or option-parser
rejection. It matches stderr, not the exit code, and stderr is script-writable,
so a consumer must bound it to one escalation per command.

## Tiered Execution

```ts
import {
  createHarness,
  localHost,
  subprocessSandbox,
  tieredSandbox,
} from "@little-stack/harness";

const harness = createHarness({
  host: localHost({
    sandbox: tieredSandbox({
      tier0: subprocessSandbox(),   // defaults to justBashSandbox() (in-process)
      nextTier: myContainerSandbox(), // any HarnessSandboxFactory you provide
      policy: { denyCommands: ["docker"] },
    }),
  }),
  model,
});
```

`nextTier` is provisioned lazily on the first escalation — a turn that never
escalates never pays for it. Build one with the shared machinery described in
[Writing a custom execution environment](/docs/v0.1.0-alpha/runtime/execution-environments#writing-a-custom-execution-environment).

**Ships in `0.2.0-alpha.3`:** if a tier wraps the tool returned by `createShellRuntime`, preserve all
execute-option keys, including symbols. Passing the options through unchanged or using
`{ ...executeOptions, abortSignal }` / `Object.assign` preserves the private, one-use
delegation token, so the adapter receives the same `context.executionId` as the outer
trace. Rebuilding options from only named string fields or serializing them drops that
context and makes the inner shell create a fresh ID. Consume the token in only the
intended delegated call; retaining or copying it cannot reuse an already-consumed ID.
Public `executionId` fields do not set attempt identity. See
[Runtime events](/docs/v0.1.0-alpha/reference/events#runtime-events).

How a turn moves:

- **Two signals escalate.** A `classifyCommand` decision of `"escalate"` switches
  before the command runs. An emulation gap found after a Tier-0 run escalates and
  retries **that command once** — the retry is the containment against forged
  stderr, and the reason classification runs first.
- **The switch is invisible to the model.** System hints always come from Tier-0
  (they feed `promptHash` replay), and one shell runtime traces every command, so
  all tiers emit identical `harness.runtime.command.*` events.
- **Escalation is sticky.** Once a turn is on the higher tier, every later command
  runs there.
- **Only env and cwd cross the switch.** Exported variables and the working
  directory are replayed into the new tier; tier-owned variables such as `PATH`
  and `HOME` are dropped.
- **Unavailable means refused, not downgraded.** When escalation is required but no
  `nextTier` is configured, or it fails to provision, the command does not run: it
  returns exit code `126` (`TIER_REFUSED_EXIT_CODE`) with a `little-harness:`
  stderr line naming the reason. Policy-denied commands are refused the same way on
  every tier.

## Events

The tier events are out-of-band: they appear in the trace and `onEvent`, never in
the prompt.

| Event | When | Metadata |
|---|---|---|
| `harness.runtime.tier.escalated` | The turn switched to `nextTier`. | `from`, `to`, `trigger` (`"classification"` or `"emulation-gap"`), `command`, `decision`/`reasons` or `gap` |
| `harness.runtime.tier.unavailable` | Escalation was needed but the higher tier could not be used. | the same, plus `detail` |
| `harness.runtime.command.denied` | `policy.denyCommands` blocked a command. | `command`, `reasons` |
| `harness.runtime.usage` | Once per turn, when the sandbox is disposed and before the turn's terminal session event (not tier-specific). | `tier` (the highest tier reached), `commands` (`tier0`, `nextTier`, `denied`), `escalations`, `sandbox` (the active tier's `HarnessSandboxUsage`: `provider`, `instanceType`, `vcpu`, `memoryGiB`, `diskGB`, `activeMs`, `awakeMs`, `costUsd`) |
| `harness.runtime.dispose.failed` | Any sandbox's teardown threw (not tier-specific). | `error` envelope |

The usage event is how LittleDB measures the Tier 0 share (turns that never
left the session folder) and the infrastructure cost per turn. Under
`tieredSandbox` the `sandbox` block is the higher tier's own `usage()` once the
turn escalated, and Tier-0's before; a tier that reports no usage of its own is
measured from its command durations and named `provider: "unknown"`. A command
retried on the higher tier after a Tier-0 emulation gap counts once on each
tier.

`little-harness doctor` counts `harness.runtime.dispose.failed` as a failure.

## Teardown And Tracked Files

A higher tier may write to the session's tracked mounts while it is disposed —
syncing a sandbox workspace back to the host, for instance. The tiered runtime
snapshots tracked mounts around its own disposal (only when the turn escalated)
and emits the usual `harness.file.*` events for whatever changed. A custom
environment that writes outside a `bash` command can do the same with
`snapshotTrackedMounts(workspace)` and
`emitTrackedMountFileChanges({ workspace, before, emit, files })`.
