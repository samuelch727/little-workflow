---
title: Durability
description: What survives a crash, what is retried, and how the runtime keeps history honest.
---

Little Workflow is at-least-once with idempotent commits. It is not exactly-once. The runtime promises that no completed step is silently re-executed and that no side effect is recorded twice for the same idempotency key, but it does not promise that an in-flight model or tool call will never run twice.

## What Survives A Process Kill

After a crash, the following state remains authoritative:

- the event log up to the last fsynced commit
- artifacts and their content-addressed blobs
- `sideEffectKey` records of external commits
- budget reservations and any debits already recorded
- skill, plugin, model, and capability locks on the WorkflowVersion

The following state does not survive and is reissued on resume:

- in-flight model calls (the worker had not yet recorded a completion event)
- in-flight tool calls without a `sideEffectKey` (these are retried)
- in-process queue intent that had not been flushed to the durable queue

A worker that resumes a run replays the event log to reconstruct state, then schedules only the steps the log does not already mark as completed.

## The Lease Model

Every worker that picks up a step acquires a lease through compare-and-set. The lease carries a monotonic `leaseToken` with a `lease_version` that increments on each successful acquisition.

```txt
acquire(stepAttemptId, currentLeaseVersion) -> { leaseToken, lease_version }
```

The token shows up on every write the worker makes during the lease:

- artifact commits include `leaseToken`
- `sideEffectKey` writes include `leaseToken`
- budget debits include `leaseToken`
- external-result attachments include `leaseToken`

Adapters reject any write whose token is stale. If a worker pauses long enough to lose its lease and another worker picks up the same step attempt, the first worker's late writes are rejected at the storage layer. Without this fence, a slow worker plus an eager retry can produce double commits.

Lease renewal is also a compare-and-set step; a worker that misses a renewal window must reacquire to continue.

## Outbox And Reconciler

External dispatches go through an outbox. A step that triggers a queue message or webhook records both the event and the outbox entry in the same transaction. The dispatcher consumes the outbox separately and marks each entry as delivered.

A reconciler watches for outbox entries that committed but were never dispatched (process killed between transaction commit and dispatch). It replays those entries. Because the entry carries the original idempotency key, the downstream system deduplicates.

This is the standard pattern; the point is that you do not need to do anything to opt in. A step that uses `sideEffectKey` and writes through the runtime's external adapters gets outbox semantics for free.

## Replay Versus Retry Versus Fork

|              | Calls models/tools | Same WorkflowVersion | Can change inputs/policy |
| ------------ | ------------------ | -------------------- | ------------------------ |
| **Replay**   | no                 | yes                  | no                       |
| **Retry**    | yes (failed step)  | yes                  | no                       |
| **Fork**     | yes                | no (new version)     | yes                      |

**Replay** is for reconstructing state after a process restart or for debugging. It reads the event log and rebuilds in-memory state without calling any external system.

**Retry** is for transient failures. It re-executes the failed step using the same WorkflowVersion and input packet, and depends on either idempotent commits or an explicit `sideEffectKey`.

**Fork** is the adaptation knob. It can change the input, model slot mapping, prompts, policy, or output schema. The result is a new WorkflowVersion that carries provenance back to the parent run.

Retry amplifies. Replay does not. Fork creates new history. Choose the verb that matches what the run actually needs.
