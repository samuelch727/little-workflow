The alpha SDK integrates with the AI SDK in one place: the default `workflowHarness` implementation in `packages/little-harness/src/workflow-harness/workflow-harness.ts`. The prior `RuntimeAiAdapter` and `PlannerAdapter` interfaces are gone — worker execution for all step types is unified through the harness (see [Harness](/docs/v0.1.0-alpha/implementation/harness)). The AI SDK's `tool({...})` from the `"ai"` package is now the canonical tool primitive — import it directly and pass it to `createToolRegistry`.

This page covers how `workflowHarness` uses the AI SDK under the hood.

## What Changed

| Prior alpha | This milestone |
|---|---|
| `RuntimeAiAdapter.generate(options)` — custom interface for AI step execution | Worker harness dispatches `ai.generate` through `workflowHarness` and the AI SDK module supplied to it |
| `createRuntimeAiAdapter(ai)` — factory passed to `runWorkflow({ ai })` | Gone. `runWorkflow` no longer accepts `ai` or `codeRunner` options. |
| `createAiSdkPlannerAdapter(ai, { model, system })` — function-only planner | Gone. Planner lives in a harness session; `WorkflowDefinition.planner.harness` is the config point. |
| Custom `ToolDescriptor` shape for tool registration | AI SDK's `tool({...})` — import from `"ai"`, use directly. |
| `code.run` signature `async (input) => output` | `async ({ input, tools }) => output` — tools proxy injected by the harness. |

## `workflowHarness` — AI SDK Usage

`workflowHarness` runs a small agent loop around the AI SDK module. When `streamText` is present it is used and the terminal promise fields are drained; otherwise the harness falls back to `generateText`. Both paths receive the same request shape: model, system, messages, tools, abort signal, and an AI SDK `output` helper.

```ts
// packages/little-harness/src/workflow-harness/workflow-harness.ts (simplified)
export const workflowHarness: Harness = {
  async run(task, ctx) {
    switch (task.kind) {
      case "plan":
        return runPlanTask(task, ctx);

      case "orchestrate":
        return runOrchestrateTask(task, ctx);

      case "execute_step":
        return runExecuteStepTask(task, ctx); // dispatches by step.uses

      case "fix_step":
        return runFixStepTask(task, ctx);
    }
  },
};
```

The agent-loop tasks configure the AI SDK request as follows:

1. **System prompt assembly**: `ctx.system` (dev-supplied) + role-specific addendum + skill frontmatter list + memory/scratch mount descriptions + available tool descriptions.
2. **Tool exposure**: passes `ctx.tools` (pre-merged by the SDK; includes role-specific injected tools) as model-facing AI SDK tools.
3. **Per-turn event recording**: before each model invocation, emits `harness.model.called`; after the response, emits `harness.model.responded`. Per tool call, emits `harness.tool_call.started(caller: "model")` + `harness.tool_call.succeeded, harness.tool_call.failed`.
4. **Durability checks**: before invoking the model, checks the event log for an existing committed `harness.model.responded` matching this turn's `promptHash` — if present, skips the model call and replays the cached response. Same for tool calls.
5. **Memory + scratch mounts**: ensures dirs exist; exposes them to the bash tool's cwd-allowlist.

## `Output.*` Mapping

For `ai.generate` steps, the step's LWIR `output` contract drives how the AI SDK call is structured:

| LWIR `output.mode` | AI SDK call |
|---|---|
| `text` | `Output.text()` |
| `object` | `Output.object({ schema })` |
| `array` | `Output.object({ schema })` with the full array schema |
| `choice` | `Output.choice({ options: values })` |
| `json` | `Output.json({})` (schema omitted) |

`aiSdkOutputSpec()` picks the helper for the step's mode. Array output intentionally uses `Output.object({ schema })` with the complete array schema rather than `Output.array()`, because the latter wraps as `{ elements: T[] }` for providers that expect a top-level object.

The harness reads structured output from `result.output` or `result.object`, and falls back to `result.text` for text-mode output.

## AI SDK Module Requirements

The default `workflowHarness` accepts an injected `aiSdkModule` so tests and custom hosts can provide the exact AI SDK instance they want. The module must expose `generateText` and the `Output` helpers used by the selected output modes. `streamText` is optional.

## Tool Interop

Tools are declared with AI SDK's `tool({...})` and registered in a `ToolRegistry`. The harness receives `ctx.tools` as executable tools, then builds a model-facing tool map before the AI SDK call: executable handlers are kept in the harness, descriptions and input schemas are exposed to the model, and plain JSON schemas are wrapped with `jsonSchema()` when the installed AI SDK module provides it.

```ts
// Dev declares:
import { tool } from "ai";
import { z } from "zod";

const fetchCandidates = tool({
  description: "Fetch candidates from ATS by job id.",
  inputSchema: z.object({ jobId: z.string() }),
  execute: async ({ jobId }) => { /* ... */ },
});

// Registered via:
const tools = createToolRegistry({ fetchCandidates });

// Passed to runWorkflow; the harness receives them via ctx.tools.
```

The AI SDK tool format is now the canonical shape. Existing code using Little Workflow's prior custom `ToolDescriptor` format needs migration — wrap with `tool({...})` from `"ai"` and pass `inputSchema` as a Zod schema.

### MCP Tools

MCP tools integrate via AI SDK's `experimental_createMCPClient`:

```ts
import { experimental_createMCPClient as createMCPClient } from "ai";

const client = await createMCPClient({ transport: /* ... */ });
const mcpTools = await client.tools();

tools.attachMcpTools(mcpTools, { prefix: "atlas" });
// Registry now has atlas.search, atlas.fetch, etc.
```

MCP-derived tools have the same `tool({...})` shape — the harness treats them identically to native tools. `harness.tool_call.started, harness.tool_call.succeeded` events record their invocations with `caller: "model"` when invoked from an agent loop.

## Cancellation And Usage

Every model turn builds one AI SDK request and records the response in the harness event log:

1. Builds a base request (model, system, messages, tools, `abortSignal`, and `output`).
2. Calls `streamText(request)` when available, otherwise `generateText(request)`.
3. Coerces the response into the harness's internal result shape with `output`, `text`, `reasoning`, `toolCalls`, and `usage`.

Usage normalization handles both AI SDK naming styles (`inputTokens`/`promptTokens`, `outputTokens`/`completionTokens`) and prefers `totalUsage` over `usage` when both present. Usage lands in `harness.model.responded.payload.response.usage` and aggregates to `harness.session.completed.payload.usage`.

The `ctx.abortSignal` is forwarded to the AI SDK request and to tool `execute()` calls via `experimental_context.abortSignal`.

## Custom Harnesses

If you need a different runtime (e.g., Cloudflare Workers, a different agent loop library), implement the `Harness` contract directly rather than wrapping `workflowHarness`:

```ts
import type { Harness } from "little-workflow";

export const customHarness: Harness = {
  async run(task, ctx) {
    // Implement agent loop using your preferred library.
    // Must emit harness.session.*, harness.model.*, and harness.tool_call.* events
    // via ctx.recorder to preserve replay + audit semantics.
    // Must honor ctx.abortSignal for cancellation.
  },
};
```

The harness contract is in `harness/types.ts`. `workflowHarness` is one implementation; the rest of the SDK doesn't depend on it directly.

## Why The Bridge Lives In One Place

Keeping all AI SDK contact in `packages/little-harness/src/workflow-harness/workflow-harness.ts` gets you:

- One place to support a new AI SDK version — feature detection, new `Output.*` helpers, new agent primitives.
- One place to add streaming. The harness internally streams from AI SDK; exposing that stream to `runWorkflow` callers is a post-alpha surface.
- One place to mock for tests. Every test that needs deterministic LLM output supplies a stub `Harness` (conforming to the `Harness` interface) rather than patching AI SDK internals.
