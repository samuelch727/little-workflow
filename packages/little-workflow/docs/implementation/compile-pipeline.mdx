title: Compile Pipeline
description: How the planner harness session turns a WorkflowDefinition into a locked WorkflowVersion, including WorkflowDefinitionHash and planner memoization.
---

Compilation is the process that turns a `WorkflowDefinition` into a hashed, immutable `WorkflowVersion` that the runtime can execute and replay. In this milestone, compilation happens **inside a planner harness session** — a full agent loop with bash, memory, scratch, and skills — rather than via a single opaque `draft()` call.

## Inputs And Outputs

```ts
// Dev-facing entry point (unchanged):
const result = await runWorkflow({
  world,
  workflows: myWorkflow,    // single workflow → planner harness session runs compile
  input,
  tools,
});
```

Internally, `runWorkflow` calls the planner harness:

```ts
const planResult = await workflow.planner.harness.run({
  kind: "plan",
  workflowSnapshot,           // WorkflowDefinitionSnapshot (id, schemas, models, tools)
  input,
}, ctx);
// → planResult.lwir: the validated LWIR
```

The result is **fully derived from inputs**. The same definition + same input + a deterministic planner = the same `workflowVersionId` and `workflowVersionHash`. Re-running the same `runId` fast-forwards via event replay without calling the model again (see [Memoization](#memoization)).

## Two Identity Primitives

This milestone introduces a second identity hash alongside `WorkflowVersion`:

| Hash | Computed when | Covers |
|---|---|---|
| `WorkflowDefinitionHash` | `createLittleWorkflow()` (authoring time) | id, schemas, planner config, models, tools, memory config |
| `WorkflowVersion` (= LWIR hash) | Planner emits LWIR (per run) | The complete LWIR graph |

`WorkflowDefinitionHash` is stable across runs as long as the definition doesn't change. It is used in the `PlannerManifest`, `OrchestratorManifest` (which references each available workflow's hash), and drift detection (see [Identity + Manifests](/docs/v0.1.0-alpha/implementation/identity-manifests)).

`WorkflowVersion` varies per run because LWIR depends on input and planner non-determinism. Two compiles producing byte-identical LWIR collapse to the same `WorkflowVersion` (content-addressed).

## Stage 1: Normalize Schemas

Same as before: JSON Schema descriptors, Zod schemas, AI SDK output helpers all funnel through `normalizeSchema()` and `normalizeOutputMode()` in `schema.ts` into a closed `NormalizedSchemaDescriptor`.

Zod schemas are converted with `z.toJSONSchema()`. Live validator functions are rejected — LWIR must never lock executable validation code.

## Stage 2: Validate Input

The supplied input is validated against the normalized input schema with Ajv (`strict: false`, `allErrors: true`). Failure throws `WorkflowInputValidationError`, which `runWorkflow()` converts into `RunFailed(causeCode: "input_schema_error")`.

## Stage 3: Snapshot Capabilities

The compiler builds a `WorkflowDefinitionSnapshot` — the view of the definition the planner harness receives:

```ts
type WorkflowDefinitionSnapshot = {
  readonly id: string;
  readonly description: string;
  readonly inputSchemaHash: string;
  readonly outputSchemaHash: string;
  readonly modelSlots: readonly { id: string; providerId: string; modelId: string; description: string }[];
  readonly plannerConfig: {
    readonly modelSlotId: string;
    readonly harnessId: string;
    readonly systemHash: string;
    readonly skillsHash: string;
  };
  readonly workerConfig: { readonly harnessId: string; readonly skillsHash: string };
  readonly globalTools: readonly string[];   // sorted tool ids
  readonly memoryConfig: { workflow: "rw" | "ro" | "none"; org: "rw" | "ro" | "none"; attached: readonly {...}[] };
};
```

Key invariants (updated vs prior alpha):

- Model slot IDs are derived from model names (e.g., `gpt-4o-mini`) with animal-suffix disambiguation on collision — no more `qualityTier`-based names like `model.fast`.
- The planner's own model is in `plannerConfig.modelSlotId`, separate from the execution `modelSlots`.
- Tool snapshots: every name in `globalTools` must exist in the registry; missing names throw `WorkflowMissingToolError`. Tool descriptions + inputSchema + outputSchema are hashed into the manifest (runtime compares at execution time, fails with `capability_drift` on mismatch).

## Stage 4: Compute PlannerManifest

The `PlannerManifest` is computed before the harness session starts:

```ts
type PlannerManifest = {
  harnessId: string;                    // "workflowHarness@1.0.0"
  plannerModelSlotId: string;
  systemPromptHash: string;
  skillsHash: string;
  workflowDefinitionHash: string;
  globalToolsHash: string;
  memoryStoreIds: ReadonlyArray<string>;
  outerLoopContextHash?: string;        // present for re-plans after supervise
};
```

`manifestHash = sha256(canonicalJson(PlannerManifest))`. Stored in `harness.session.started` at session start.

## Stage 5: Drift Check On Resume

If this `runId` has a prior `harness.session.started` event for the planner:

```ts
const stored = findEvent(events, "harness.session.started", { role: "planner" });
const currentHash = sha256(canonicalJson(currentPlannerManifest));
if (stored.payload.manifestHash !== currentHash) {
  throw new CapabilityDriftError({ stored, current, diff });
}
```

The planner session is fast-forwarded from events (see [Memoization](#memoization)) rather than re-run.

## Stage 6: Planner Harness Session

The planner harness session is a full agent loop. The default `workflowHarness` calls AI SDK `streamText` when available, otherwise `generateText`:

```ts
workflowHarness.run({
  kind: "plan",
  workflowSnapshot,
  input,
}, ctx)
```

The session has access to:

- **bash** — cwd-scoped to `/mnt/scratch/own/`. The planner can write draft LWIR to scratch, run `node` to test code bodies, and iterate.
- **Memory** — `/mnt/memory/workflow/` (rw by default), `/mnt/memory/org/` (ro by default). Planner reads prior lessons when designing.
- **Skills** — skill frontmatter injected into the system prompt; bodies readable via `cat .agents/skills/<name>/SKILL.md`.
- **Tool descriptors** (read-only for planning) — planner sees tool descriptions + schemas to write valid LWIR step `with.tools` allowlists but does not execute tools.

The planner iterates within its own agent loop until it produces a valid LWIR. Validation happens inside the harness session (the model uses bash to test code bodies, introspects schemas, repairs its own output). The outer compile pipeline sees one final LWIR per planner session.

The planner lifecycle events from the prior alpha (`PlannerStarted`, `PlannerDraftedWorkflow`, `WorkflowValidationFailed`, `WorkflowValidationSucceeded`) are now represented as `harness.model.called, harness.model.responded, harness.tool_call.started, and harness.tool_call.succeeded` events inside the planner's session. `OrchestrationRequested` and `WorkflowVersionRegistered` remain as run-level events.

## Stage 7: LWIR Validation

When the planner's agent loop commits a terminal output, `validateLwir()` from `lwir.ts` runs. The binding pass then ties the LWIR back to the snapshot:

- `metadata.name` must equal the workflow's `id`.
- `sha256(input.schema)` must equal the snapshot's input schema hash.
- `sha256(output.schema)` must equal the snapshot's output schema hash.
- `permissions.models` / `permissions.tools` must be subsets of the capability snapshot.
- Every `ai.*` step `with.model` must be in the allowed model slot set.
- Every `tool.call` step `with.tool` must be in the allowed tools.

Findings have a stable shape:

```json
{
  "severity": "error",
  "code": "binding.input_schema_mismatch",
  "path": "$.input.schema",
  "message": "LWIR input schema must match the workflow definition's input schema."
}
```

If validation fails, the harness's agent loop receives the findings and repairs (the model iterates again within the same session). The outer compile pipeline sees the final valid LWIR only.

## Stage 8: Register And Lock

When validation passes, `registerWorkflowVersion(lwir)` produces a `WorkflowVersion`:

```json
{
  "id": "wfver_4f0aab7d12345678",
  "hash": "sha256:...",
  "canonicalizer": "little-workflow-canonical-json@alpha",
  "canonicalJson": "{\"apiVersion\":\"littleworkflow.dev/v0.1\",...}",
  "lwir": { ... }
}
```

`WorkflowVersion = sha256(canonicalJson(LWIR))` — unchanged.

`compiler-lock.ts` wraps it with a lock:

```json
{
  "workflowVersionId": "wfv_4f0aab7d12345678",
  "workflowVersionHash": "sha256:...",
  "lwirVersionId": "wfver_4f0aab7d12345678",
  "lwirHash": "sha256:...",
  "workflowDefinitionHash": "sha256:...",
  "inputSchemaHash": "sha256:...",
  "requestedOutput": { "mode": "object", "schema": { ... } },
  "requestedOutputHash": "sha256:...",
  "capabilityManifest": { ... },
  "capabilityManifestHash": "sha256:...",
  "modelSlots": [ ... ],
  "tools": [],
  "validationHash": "sha256:..."
}
```

## Memoization

The planner harness session is durable — every model call and tool call within the session is event-logged. On resume with the same `runId`:

1. Events are replayed — completed `harness.model.called, harness.model.responded` pairs fast-forward without re-calling the model.
2. Completed `harness.tool_call.started, harness.tool_call.succeeded` pairs replay their results.
3. Only the in-flight call (the one with no terminal event) is re-executed.

This is identical to LWIR per-step memoization, applied at the harness session level. Re-running the same `(runId, workflowDefinition, input)` is deterministic via event replay.

## Outer-Loop Context

When `maxOuterCycles > 1`, the planner harness session's `PlannerManifest` carries an `outerLoopContextHash` (sha256 of prior cycles). Each cycle's manifest differs → each cycle's `manifestHash` differs → resume correctly distinguishes which cycle's session to fast-forward.

The planner's agent loop receives prior cycle information in the task context:

```ts
type PlanTask = {
  readonly kind: "plan";
  readonly workflowSnapshot: WorkflowDefinitionSnapshot;
  readonly input: unknown;
  readonly outerLoopContext?: {
    readonly cycleNumber: number;
    readonly maxCycles: number;
    readonly isFinalCycle: boolean;
    readonly priorCycles: ReadonlyArray<{ cycleNumber; status; output; summary? }>;
  };
};
```

## What This Buys

- The planner can test code before emitting LWIR — iterate in bash scratch, read prior lessons from memory, embed validated code bodies.
- The same `(runId, definition, input)` always yields the same LWIR (fast-forwarded from event cache after first compile).
- The runtime verifies the LWIR matches the lock before running a step — no trust in the planner is required at runtime.
- `WorkflowDefinitionHash` (new) provides stable identity across many LWIR compiles of the same definition, enabling orchestrator-level drift detection.

## Inspecting Compile Stages

After a `runWorkflow` call, the event log contains:

```
harness.session.started   (role: "planner")
harness.model.called      (turn 1 — planner reasons about the workflow)
harness.model.responded   (turn 1)
harness.tool_call.started  (caller: "model", bash — tests code body in scratch)
harness.tool_call.succeeded
harness.model.called      (turn 2 — refines LWIR)
harness.model.responded   (turn 2 — produces valid LWIR)
harness.session.completed
WorkflowVersionRegistered
RunStarted
```

`little events <run-id>` surfaces the full sequence. See [Event Log](/docs/v0.1.0-alpha/implementation/event-log) for payload shapes.
