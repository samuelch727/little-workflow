---
title: Create A Workflow
description: The primary authoring surface for planned Little Workflow jobs.
---

`createLittleWorkflow()` is the main front door. It describes a job the compiler can turn into a bounded, validated workflow.

The definition should stay declarative. It should explain what the workflow needs, what it can use, what output it must produce, and which policies limit execution.

```ts
const candidateReview = createLittleWorkflow({
  id: "candidate.review",
  description:
    "Review each candidate against the job requirement and produce evidence-backed decision support.",
  inputSchema: z.object({
    jobRequirement: z.string(),
    candidateArray: z.array(
      z.object({
        candidateId: z.string(),
        pdf: z.url(),
        taleoXml: z.url(),
      }),
    ),
  }),
  output: Output.object({
    schema: z.object({
      candidates: z.array(
        z.object({
          candidateId: z.string(),
          isCandidateFit: z.boolean(),
          isCandidateFitReason: z.string(),
          candidateOverview: z.string(),
          candidateMarkdown: z.string(),
        }),
      ),
    }),
  }),
  models: [plannerModel, fastWorkerModel, verifierModel],
  planner: plannerModel,
  globalTools: {
    parsePdf: parsePdfTool,
  },
  toolSelection: "planner_selected",
});
```

## Authoring Rules

- Use Zod for developer-facing input, output, and tool schemas.
- Pass AI SDK model objects and tool definitions at the control-plane boundary.
- Use `model()` when production governance needs explicit role, limits, capabilities, pricing, or disclosure metadata.
- Put runtime infrastructure in [`runWorkflow()`](/docs/v0.1.0-beta/run-inspect/run-workflow) or `createRuntime()`, not the definition.
- Treat examples in docs as the target API until the package implementation lands.

## Tool Selection

`toolSelection` controls how the planner can reference workflow tools:

```ts
type ToolSelectionPolicy = "planner_selected" | "all" | "explicit_only";
```

`planner_selected` is the default teaching path. The planner may choose from `globalTools`, but every selected tool becomes an explicit capability ref in LWIR and must pass policy validation before execution.

## The Compiler Boundary

The compiler does not serialize executable model objects or tool functions into LWIR. It compiles them into stable refs, schema hashes, lock entries, policy snapshots, and cost/risk metadata.

That is what makes the workflow durable and auditable.
