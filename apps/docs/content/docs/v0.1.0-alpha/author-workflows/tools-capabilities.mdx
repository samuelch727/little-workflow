Tools in Little Workflow are AI SDK `tool({...})` values. The developer registers them in a `ToolRegistry`; the workflow references them by name in `globalTools`; the harness dispatches them at execution time.

## Defining A Tool

Use `tool()` from the `ai` package:

```ts
import { tool } from "ai";
import { z } from "zod";

const fetchCandidates = tool({
  description: "Fetch candidates from ATS by job id.",
  inputSchema: z.object({
    jobId: z.string(),
  }),
  outputSchema: z.object({
    candidates: z.array(z.object({
      id: z.string(),
      name: z.string(),
      resume: z.string(),
    })),
  }),
  execute: async ({ jobId }) => {
    const res = await fetch(`https://ats.example.com/candidates?jobId=${jobId}`);
    return res.json();
  },
});
```

Little Workflow does not introduce a custom descriptor shape. Any AI SDK `tool()` value works — including tools you already use in chat apps or generation pipelines.

## Creating A Registry

`createToolRegistry` is a thin typed wrapper around a `Record<string, AiSdkTool>`. Pass your tools as the initial map:

```ts
import { createToolRegistry } from "little-workflow";
import { tool } from "ai";

const tools = createToolRegistry({
  fetchCandidates: tool({ /* ... */ }),
  scoreCandidate: tool({ /* ... */ }),
  lookupBackgroundCheck: tool({ /* ... */ }),
});
```

The registry is mutable (new tools can be registered at any time) but immutable per-entry: re-registering an existing name with a different descriptor throws. Ids follow the pattern `[a-zA-Z][a-zA-Z0-9_.-]*` — dots are allowed for namespacing (e.g., MCP-prefixed `atlas.search`).

## Workflow Tool Scope

```ts
import { createLittleWorkflow } from "little-workflow";
import { z } from "zod";

const candidateReview = createLittleWorkflow({
  id: "candidate.review",
  inputSchema: z.object({ /* ... */ }),
  outputSchema: z.object({ /* ... */ }),
  // ...
  globalTools: ["fetchCandidates", "scoreCandidate"],  // names only
});
```

`globalTools` is a `readonly string[]` of names registered in the registry. Every name must exist in the registry when `runWorkflow` starts; a missing name throws `WorkflowMissingToolError`.

The planner sees tool descriptions and schemas (to design valid LWIR steps with `with.tools` allowlists) but does not execute them — tools are for the Worker role. LWIR steps reference tools from this allowlist; the harness enforces the constraint at runtime.

## MCP Integration

AI SDK ships an experimental MCP client. Little Workflow uses it as-is — you manage the client lifecycle and pull tools from it as AI SDK `tool()` values:

```ts
import { experimental_createMCPClient as createMCPClient } from "ai";
import { Experimental_StdioMCPTransport as StdioMCPTransport } from "ai/mcp-stdio";
import { createToolRegistry, runWorkflow } from "little-workflow";

// 1. Create and manage the MCP client lifecycle.
const atlasClient = await createMCPClient({
  transport: new StdioMCPTransport({
    command: "node",
    args: ["./mcp-servers/atlas-mcp.mjs"],
  }),
});

// 2. Pull tools (already in AI SDK shape).
const atlasTools = await atlasClient.tools();
// Returns: { search: tool({...}), fetch: tool({...}), summarize: tool({...}) }

// 3. Compose into the registry with a prefix to avoid name collisions.
const tools = createToolRegistry({
  fetchCandidates,
  scoreCandidate,
});
tools.attachMcpTools(atlasTools, { prefix: "atlas" });
// Registry now has: fetchCandidates, scoreCandidate, atlas.search, atlas.fetch, atlas.summarize

await runWorkflow({ world, workflows, input, tools });

// 4. Close the client when done.
await atlasClient.close();
```

### Transports

Any AI SDK-supported MCP transport works: Stdio, HTTP/SSE, WebSocket. Little Workflow doesn't constrain the transport choice.

### Prefix Convention

Use a prefix when attaching MCP tools to avoid name collisions:

```ts
tools.attachMcpTools(atlasTools, { prefix: "atlas" });   // search → atlas.search
tools.attachMcpTools(legalTools, { prefix: "legal" });   // search → legal.search
```

If a name still collides after prefixing (or if you attach without a prefix and two servers both export `search`), `attachMcpTools` throws at registration time.

### Lifecycle Responsibility

Create the MCP client before passing the registry to `runWorkflow`. Close it after all runs that use the registry are done. Reconnection and pooling are out of alpha scope.

## `code.run` Tools Proxy

`code.run` steps receive `{ input, tools }`. The `tools` object is a proxy over all globally-registered tools — callable as async functions, no model in the loop. This saves tokens vs routing through the model for deterministic data operations:

```ts
// LWIR step (shown in expanded form for readability):
{
  "id": "filter-top-candidates",
  "uses": "code.run",
  "needs": ["fetch"],
  "with": {
    "source": `
      async ({ input, tools }) => {
        const { candidates } = await tools.fetchCandidates({ jobId: input.jobId });
        const filtered = candidates.filter(c => c.score > 0.8);
        const enriched = await Promise.all(
          filtered.map(c => tools.lookupBackgroundCheck({ candidateId: c.id }))
        );
        return { count: enriched.length, top: enriched.slice(0, 5) };
      }
    `
  },
  "input": { "jobId": "{{ input.jobId }}" },
  "output": {
    "mode": "object",
    "schema": { "type": "object", "properties": { "count": {"type": "integer"}, "top": {"type": "array"} } }
  }
}
```

The model never sees the raw candidate list. Every tool invocation from code is event-logged with `caller: "code"` — distinguishable from model-driven calls in `little events`.

`code.run` steps have access to all `globalTools` (no per-step allowlist). The code body is auditable (visible in the LWIR's `with.source`), so unrestricted tool access is intentional.

### Signature Change vs Prior Alpha

Prior alpha code bodies used `async (input) => output`. The new signature is:

```diff
- async (input) => {
+ async ({ input, tools }) => {
    // ...
  }
```

If your existing code body doesn't call tools, the change is just the destructuring at the parameter.

## What The Compiler Does With Tools

At compile time:

- Each name in `globalTools` is read from the registry and its descriptor (`description` + `inputSchema` + `outputSchema`) is hashed into the `WorkflowVersion` capability snapshot.
- Names not in the registry fail with `WorkflowMissingToolError`.
- The planner sees tool descriptions and schemas when designing LWIR; it cannot invent new tools.

At execution time:

- The harness reads the `execute` function from the registry by name, validates input against `inputSchema`, and invokes it.
- The live descriptor hash is compared against the locked snapshot. A mismatch raises `RuntimeCapabilityDriftError` (`causeCode: "capability_drift"`). Re-run `runWorkflow()` to produce a fresh `WorkflowVersion`. The failed run is preserved in Local World for inspection.

Implementation bodies (`execute`) are deliberately excluded from the descriptor hash — only the schema surface is locked. See [Security Model](/docs/v0.1.0-alpha/governance/security-model).
