This page is a concrete trace of one workflow through the compile pipeline. Every JSON snippet here is the shape the alpha SDK produces; the contents are abbreviated for readability.

The key change in this milestone: the planner now operates inside a **harness session** — a full agent loop with bash, memory, scratch, and skills — rather than a single opaque `draft()` call. The LWIR shape is unchanged.

## The Workflow

```ts
import { createLittleWorkflow, model } from "little-workflow";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const summarizeTicket = createLittleWorkflow({
  id: "support.summarize-ticket",
  description: "Summarize a support ticket and classify its severity.",

  inputSchema: z.object({
    ticketId: z.string(),
    transcript: z.string(),
  }),

  outputSchema: z.object({
    summary: z.string(),
    severity: z.enum(["low", "medium", "high"]),
  }),

  // Execution model slots (the planner chooses among these in LWIR step with.model)
  models: [
    model(openai("gpt-5"), {
      description: "Strong reasoning model for complex analysis.",
    }),
    model(openai("gpt-4o-mini"), {
      description: "Fast model for short structured outputs.",
    }),
    // Slot ids auto-derived: "gpt-5" (first wins clean name), "gpt-4o-mini"
  ],

  // Planner — required
  planner: {
    model: openai("gpt-5"),      // planner's own model (separate from execution models)
    system: "You design support-ticket workflows. Test code in scratch before committing.",
  },
});
```

Input:

```json
{
  "ticketId": "TCK-123",
  "transcript": "Customer reports intermittent billing export failures..."
}
```

## Stage A: WorkflowDefinitionSnapshot

`toOrchestrationRequest()` normalizes schemas, snapshots capabilities, and produces a `WorkflowDefinitionSnapshot`. This is the only view of the definition the planner harness receives:

```json
{
  "id": "support.summarize-ticket",
  "description": "Summarize a support ticket and classify its severity.",
  "inputSchemaHash": "sha256:...",
  "outputSchemaHash": "sha256:...",
  "modelSlots": [
    {
      "id": "gpt-5",
      "providerId": "openai",
      "modelId": "gpt-5",
      "description": "Top reasoning model. Good for complex planning, multi-step reasoning, schema design."
    },
    {
      "id": "gpt-4o-mini",
      "providerId": "openai",
      "modelId": "gpt-4o-mini",
      "description": "Fast model for short structured outputs."
    }
  ],
  "plannerConfig": {
    "modelSlotId": "gpt-5",
    "harnessId": "workflowHarness@1.0.0",
    "systemHash": "sha256:...",
    "skillsHash": "sha256:..."
  },
  "workerConfig": {
    "harnessId": "workflowHarness@1.0.0",
    "skillsHash": "sha256:..."
  },
  "globalTools": [],
  "memoryConfig": {
    "workflow": "rw",
    "org": "ro",
    "attached": []
  }
}
```

Notes:

- `modelSlots` uses slot ids derived from model names (e.g., `gpt-5`, `gpt-4o-mini`) — no `qualityTier` fields.
- The planner's own model (`openai("gpt-5")`) is in `plannerConfig.modelSlotId`, separate from the execution `modelSlots`. The planner uses this model for its own agent loop, not for LWIR step execution.
- Tool descriptions + inputSchema + outputSchema are hashed. The runtime compares hashes at execution time.

The `WorkflowDefinitionHash = sha256(canonicalJson(WorkflowDefinitionSnapshot))` is computed once here and stays stable across many LWIR compiles for this definition (see [Identity + Manifests](/docs/v0.1.0-alpha/implementation/identity-manifests)).

## Stage B: Planner Harness Session

The planner harness session is a full agent loop. It receives:

- The `WorkflowDefinitionSnapshot` + `input` as the task.
- `ctx.system`: the dev's system prompt (`"You design support-ticket workflows..."`) merged with the SDK's planner addendum.
- `ctx.bash`: cwd-scoped to `/mnt/scratch/own/`.
- `ctx.memoryMounts`: `/mnt/memory/workflow/` (rw), `/mnt/memory/org/` (ro).
- `ctx.tools`: tool descriptors (read-only; the planner designs LWIR that references tools but does not execute them).

The planner's agent loop might:

```bash
# Check prior lessons before designing:
cat /mnt/memory/workflow/lessons-learned.md

# Test a code body in scratch before embedding it in LWIR:
cat > /mnt/scratch/own/step-A.js << 'EOF'
async ({ input, tools }) => {
  return { summary: input.transcript.slice(0, 200), severity: "medium" };
}
EOF

# Iterate until satisfied, then emit LWIR as the terminal output.
```

The planner emits LWIR as the agent loop's terminal output. The compiler validates it; if validation fails, the findings are fed back into the harness's conversation and the agent iterates.

## Stage C: LWIR Draft

A typical first LWIR for the example above (abbreviated):

```json
{
  "apiVersion": "littleworkflow.dev/v0.1",
  "kind": "Workflow",
  "metadata": {
    "name": "support.summarize-ticket",
    "version": "0.1.0",
    "description": "Summarize a support ticket and classify severity."
  },
  "input": {
    "schema": {
      "type": "object",
      "required": ["ticketId", "transcript"],
      "properties": {
        "ticketId": { "type": "string" },
        "transcript": { "type": "string" }
      }
    }
  },
  "output": {
    "schema": {
      "type": "object",
      "required": ["summary", "severity"],
      "properties": {
        "summary": { "type": "string" },
        "severity": { "type": "string", "enum": ["low", "medium", "high"] }
      }
    }
  },
  "permissions": {
    "models": ["gpt-4o-mini"],
    "tools": [],
    "secrets": [],
    "network": []
  },
  "steps": [
    {
      "id": "summarize",
      "uses": "ai.generate",
      "needs": [],
      "with": {
        "model": "gpt-4o-mini",
        "prompt": "Summarize ticket {{ input.ticketId }} based on this transcript:\n{{ input.transcript }}\nReturn a 1-2 sentence summary and a severity from low|medium|high."
      },
      "output": {
        "mode": "object",
        "schema": {
          "type": "object",
          "required": ["summary", "severity"],
          "properties": {
            "summary": { "type": "string" },
            "severity": { "type": "string", "enum": ["low", "medium", "high"] }
          }
        }
      }
    }
  ]
}
```

Notes about the LWIR shape (unchanged from prior alpha):

- `permissions.models` uses slot ids (`"gpt-4o-mini"`) — the new derivation rule, not `qualityTier` names.
- `step.uses` is `ai.generate`.
- `onFailure.fixer` is an optional new field on `code.run` steps (see below).

## `onFailure.fixer` Field (New)

`code.run` steps can optionally declare a fixer for self-recovery on failure:

```jsonc
{
  "id": "compute-score",
  "uses": "code.run",
  "with": {
    "source": "async ({ input, tools }) => { /* ... */ }"
  },
  "output": {
    "mode": "object",
    "schema": { "type": "object", "properties": { "score": { "type": "number" } } }
  },
  "onFailure": {
    "fixer": {
      "model": "gpt-4o-mini",      // slot id from workflow.models
      "maxAttempts": 3,
      "system": "Fix the code so it returns output matching the schema. Test in scratch."
    }
  }
}
```

When a `code.run` step fails, the runtime checks for `onFailure.fixer`. If declared, a fixer harness session (`kind: "fix_step"`) is spawned. The fixer has the failed code body, the error, and the output schema. On success, `harness.session.completed.fixedSource` carries the repaired code. See [Fixer](/docs/v0.1.0-alpha/implementation/fixer).

## Stage D: Validation And Repair

`validateLwir()` runs from `lwir.ts`. The binding pass then ties the LWIR back to the snapshot:

- `metadata.name` must equal the workflow's `id`.
- `sha256(input.schema)` must equal `inputSchemaHash`.
- `sha256(output.schema)` must equal `outputSchemaHash`.
- `permissions.models` must be a subset of the snapshot's `modelSlots`.
- Every `ai.*` step `with.model` must be in the allowed model slot set.
- Every `tool.call` step `with.tool` must be in `globalTools`.

Findings returned to the harness:

```json
{
  "severity": "error",
  "code": "binding.model_disallowed",
  "path": "$.steps[0].with.model",
  "message": "Model slot 'gpt-5' is not in the workflow's modelSlots list."
}
```

## Stage E: Registration

When validation passes, `registerWorkflowVersion(lwir)` returns:

```json
{
  "id": "wfver_4f0aab7d12345678",
  "hash": "sha256:...",
  "canonicalizer": "little-workflow-canonical-json@alpha",
  "canonicalJson": "{\"apiVersion\":\"littleworkflow.dev/v0.1\",...}",
  "lwir": { ... }
}
```

`compiler-lock.ts` wraps it with a lock:

```json
{
  "workflowVersionId": "wfv_4f0aab7d12345678",
  "workflowVersionHash": "sha256:...",
  "lwirVersionId": "wfver_4f0aab7d12345678",
  "lwirHash": "sha256:...",
  "workflowDefinitionHash": "sha256:...",
  "inputSchemaHash": "sha256:...",
  "requestedOutput": { "mode": "object", "schema": { ... } },
  "requestedOutputHash": "sha256:...",
  "capabilityManifest": { ... },
  "capabilityManifestHash": "sha256:...",
  "modelSlots": [
    { "slotId": "gpt-5", "metadataHash": "sha256:...", "modelIdentityHash": "sha256:..." },
    { "slotId": "gpt-4o-mini", "metadataHash": "sha256:...", "modelIdentityHash": "sha256:..." }
  ],
  "tools": [],
  "validationHash": "sha256:..."
}
```

`runWorkflow()` carries this lock into the runtime. When the executor sees a step that references `gpt-4o-mini`, it looks up the model binding, confirms the live `modelIdentityHash` matches the locked one, and dispatches. Any mismatch is `capability_drift`.

## Outer-Loop Context

When `maxOuterCycles > 1`, each cycle's `PlanTask` carries an `outerLoopContext`:

```ts
outerLoopContext?: {
  cycleNumber: number;       // 1-indexed
  maxCycles: number;
  isFinalCycle: boolean;
  priorCycles: ReadonlyArray<{
    cycleNumber: number;
    status: "completed" | "failed";
    output: unknown;
    summary?: string;
  }>;
};
```

The planner harness session receives this in its task. The `PlannerManifest` carries `outerLoopContextHash = sha256(canonicalJson(priorCycles))` — each cycle's manifest is distinct, enabling correct drift detection on resume.

## What This Means For The Planner

- The planner is **never** in the loop at runtime. Its job ends once registration succeeds; worker harness sessions execute the LWIR.
- The planner's output is hashable JSON. The runtime never parses natural language to dispatch a step.
- The planner CAN use bash, memory, and skills during design — this is a capability the prior function-only `draft()` call did not provide.
- The planner is allowed to iterate internally. Findings are structured; the repair loop is within the planner's own agent loop.

## Inspecting These Stages

When a planner-backed `runWorkflow()` runs, the event log contains:

```
harness.session.started   (role: "planner"; manifest; manifestHash)
harness.model.called      (turn 1 — planner reasons about the workflow)
harness.model.responded   (turn 1 — possibly with bash tool calls)
harness.tool_call.started  (caller: "model", toolName: "bash", ...)
harness.tool_call.succeeded
harness.model.called      (turn 2 — refines draft, fixes validation issue)
harness.model.responded   (turn 2 — emits valid LWIR)
harness.session.completed (output: the LWIR)
WorkflowVersionRegistered
RunStarted
```

`little events <run-id>` surfaces the full sequence. See [Event Log](/docs/v0.1.0-alpha/implementation/event-log) for payload shapes.
