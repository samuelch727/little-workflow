Local World is the alpha development backend for Little Workflow.

It lets developers compile, run, inspect, and replay workflows without Postgres, Redis, S3, or cloud accounts.

```ts
await runWorkflow({
  world: localWorld({ dataDir: ".little-workflow" }),
  workflows: myWorkflow,
  input: myInput,
});
```

## Options

```ts
type LocalWorldOptions = {
  dataDir?: string;
  maxConcurrentSteps?: number;
};
```

- **`dataDir`** — root directory for all world state. Defaults to `.little-workflow` in the current working directory.
- **`maxConcurrentSteps`** — caps total in-flight step attempts across all parallel groups and serial steps in a run. Effective concurrency at any moment is `min(group.maxConcurrency, world.maxConcurrentSteps - in-flight)`. Default `undefined` (no cap). For compute-heavy workflows, `os.availableParallelism()` is a sensible starting value. The cap gates all step executions; `parallel` container dispatch itself is excluded to avoid deadlock.

```ts
import os from "node:os";
import { localWorld } from "little-workflow";

const world = localWorld({
  dataDir: ".little-workflow",
  maxConcurrentSteps: os.availableParallelism(),
});
```

## Directory Layout

The Local World data directory is self-contained. Events are stored in one SQLite/WAL database keyed by run id; artifacts and outer-loop manifests remain ordinary files.

```txt
.little-workflow/
  events/
    events.db              ← SQLite event rows for every run
    events.db-wal          ← WAL sidecar, when active
    events.db-shm          ← SQLite shared-memory sidecar, when active
  artifacts/
    art_123.json
    blobs/
      art_123.bin
  locks/
  outer-loops/
    ol_abc123.json
```

Events are committed as SQLite rows and exposed through `world.listEvents(runId)` and `little events <runId>`. Artifacts live as files on the local filesystem with a small JSON manifest per artifact. Production databases, distributed queues, and remote blob storage arrive in [v0.1.0-beta](/docs/v0.1.0-beta/run-inspect/local-world) and later.

### `events/`

Every workflow run, orchestrator run, and sub-workflow run writes to `<dataDir>/events/events.db`. The event table uses `(run_id, sequence)` as its primary key, so each run still has an independent ordered event stream even though the bytes live in one database.

For pipeline runs (array of workflows + orchestrator), the orchestrator is the top-level run and sub-workflow runs are linked by events. Sub-run `runId`s are reserved in the orchestrator's event stream via `harness.tool_call.started.payload.args.subRunId` and returned via `harness.tool_call.succeeded.payload.result.runId`.

### `memory/`

Memory stores persist across runs. Three scopes:

| Store | On-disk path | Harness mount | Default mode |
|---|---|---|---|
| Workflow | `memory/workflows/<workflowId>/` | `/mnt/memory/workflow/` | `rw` by that workflow's planners; `ro` by workers |
| Pipeline | `memory/pipelines/<pipelineKey>/` | `/mnt/memory/pipeline/` | `rw` by the orchestrator; `ro` by planners + workers of sub-runs |
| Org | `memory/org/` | `/mnt/memory/org/` | `ro` by all roles (override requires `memory: { org: "rw" }` on the workflow) |

`<pipelineKey>` is a hash of the orchestrator's sorted set of available `WorkflowDefinitionHash` values. Runs with the same pipeline composition share a pipeline memory store.

Memory stores are created lazily on first write. Workflow memory is keyed by `workflowId`; changing the workflow id creates a new store. Devs may pre-populate the org store with policies, runbooks, or style guides before running any workflow.

See [Memory](/docs/v0.1.0-alpha/author-workflows/memory) for the memory model, mount semantics, and memory poisoning mitigations.

### `outer-loops/`

When `maxOuterCycles > 1`, the runtime writes a manifest per outer-loop session:

```jsonc
// outer-loops/{outerLoopId}.json
{
  "outerLoopId": "ol_…",
  "goal": { "workflowDefinitionHash": "…", "description": "…" },
  "maxCycles": 5,
  "cycles": [
    {
      "cycleNumber": 1,
      "runId": "run_…",
      "workflowVersionId": "wv_…",
      "status": "completed",
      "output": { }
    }
  ],
  // pendingCycleRunId is set before a cycle starts and cleared after supervise completes
  "pendingCycleRunId": "run_…",
  // result is set when supervise returns { kind: "done" }
  "result": { "kind": "done", "finalOutput": { } }
}
```

The manifest is written via atomic rename (write to `*.tmp`, rename into place) after every `OuterLoopCycleCompleted` event. See [Durability](/docs/v0.1.0-alpha/run-inspect/durability) for the resume scenarios this enables.

## API Shape

The `LocalWorld` API is unchanged. Code should depend on runtime APIs, not the on-disk layout:

- `runWorkflow()`
- `localWorld()`
- `listEvents()`
- `replayRun()`

The on-disk layout described above is an implementation detail. It grew to support memory stores and nested sub-runs, but the API surface is stable. Store interfaces, `SkillStore`, and `PluginStore` arrive in later versions when production adapters, skills, and plugins exist.

## Limits

Local World is not production-grade:

- no distributed workers
- no production locking
- no multi-tenant isolation beyond directory separation
- no presigned multipart upload flow
- no production queue backend
- memory stores are plain files with no versioning, audit log, or concurrent-write protection (single-process assumption)

The first alpha demo proves kill-and-resume behavior: stop a run mid-flight, restart, replay persisted events, and continue without re-calling completed model or tool steps. The second demo exercises orchestrator + memory: an orchestrator reads accumulated pipeline memory on each run, writing better plans over time.
