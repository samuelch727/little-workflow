A **workspace** lets you keep many harnesses in one repo, each as its own folder under `agents/`. A
folder is loaded into a runnable harness by auto-discovering its `tools/`, `skills/`, and `workflows/` — `createHarness`
itself is unchanged, and inline `createHarness(...)` still works exactly as before.

## Layout

The workspace marker `little-harness.json` (`{ "agents": "agents" }`) sits at the root; each agent is a
folder under `agents/`, named by the agent's id:

## `agent.ts`

The entry is a plain `createHarness` call. Tools, skills, and workflows are omitted here — they are
discovered from the folder and merged in when the agent is loaded.

```ts
import { createHarness, localHost } from "@little-stack/harness";
import { anthropic } from "@ai-sdk/anthropic";

export default createHarness({
  model: anthropic("claude-opus-4-6"), // set the selected provider's required env vars
  system: "You are a support agent.", // or omit and use instructions.md
  host: localHost(),
});
```

When generated by `little-harness init`, the provider import and model id come from the AI SDK
provider/model selected in the wizard — the `openai` provider is the default. The wizard currently
offers 24 provider choices: the official AI SDK language-model providers plus a custom OpenAI-compatible API scaffold. You can also type a custom
provider model id when the exact model is not listed.

If both `agent.ts`'s `system` and a sibling `instructions.md` exist, `agent.ts` wins; if `system` is
omitted, `instructions.md` becomes the system prompt.

## Tools — `tools/*.ts`

Each file default-exports a normal AI SDK tool; the tool name is the filename without extension. Inline
`tools` passed to `createHarness` win on a name collision.

```ts
// tools/lookup_order.ts
import { tool } from "ai";
import { z } from "zod";

export default tool({
  description: "Look up an order by id.",
  inputSchema: z.object({ orderId: z.string() }),
  execute: async ({ orderId }) => ({ orderId, status: "shipped" }),
});
```

## Skills — `skills/<name>/`

Each subdirectory is one skill:

- `SKILL.md` only → a **local** skill (`skill("./skills/<name>")`).
- `skill.ts` (default-exports `skill(...)`) → a **declared** skill — used directly. This is how you pull
  in **remote/GitHub** skills, and it wins over a sibling `SKILL.md`.

```ts
// skills/frontend-design/skill.ts
import { skill } from "@little-stack/harness";
export default skill("https://github.com/anthropics/skills#v1.2.0", { skills: ["frontend-design"] });
```

Remote skills resolve, pin (by commit), and stage exactly as when passed inline to `createHarness` — at
runtime local and remote skills are both staged under `.agents/skills/<name>/`.

## Workflows — `workflows/*.ts`

Each file default-exports a `HarnessWorkflow` — typically a Little Workflow adapted with
`asHarnessWorkflow` — and becomes one tool named from the workflow id. Discovered workflows are appended
to any `workflows` passed in `agent.ts`. Test and spec files are skipped.

```ts
// workflows/refund.ts
import { asHarnessWorkflow, defineWorkflow } from "@little-stack/workflow";

const refund = defineWorkflow({ id: "billing.refund", /* input, output, model, tools */ });

export default asHarnessWorkflow(refund, { definitionIdentity: "billing.refund@1" });
```

A bare `defineWorkflow(...)` default export is rejected at load time: it has no `executionMode` or
`definitionIdentity`. See [Triggering a workflow from an agent](/docs/v0.1.0-alpha/build-agents/workflows)
for the tool result shape and `workflowBudgets`.

## Schedules — `schedules/*.ts`

Each file default-exports `defineSchedule({ cron, prompt })`, a run of the agent
on a timer; the file name is its id. `loadHarness()` ignores them;
`little-harness dev` and `start` run them. See
[Serving An Agent](/docs/v0.1.0-alpha/build-agents/serving-agents#schedules--schedulests).

```ts
// schedules/morning-backlog.ts
import { defineSchedule } from "@little-stack/harness";

export default defineSchedule({
  cron: "0 9 * * 1-5",
  timezone: "Asia/Hong_Kong",
  prompt: "Pre-approve every application received since yesterday.",
});
```

## Connectors And UI

`connectors/` is reserved for connection layers such as Slack, Telegram, or web chat routes. It is
ignored by `loadHarness()`. `little-harness start` serves each one at `/connectors/<id>`; in your
own server, use `loadChatSdkConnector()` or `loadWebRichConnector()` from
`@little-stack/harness/connectors/runtime` when a route wants to expose an agent through a chat surface.
String connector ids still work from the runtime subpath; the loaders import discovery dynamically
when needed. Use `@little-stack/harness/connectors` when the route directly calls discovery helpers such as
`discoverConnectors()`.

Simple connectors can be flat files like `connectors/slack.ts`. Use nested connector folders when the
connector owns extra files:

```txt
connectors/
  slack/
    connector.ts
    tools/
      add_reaction.ts
    renderers/
      lookup_order.tsx
```

Connector tool extensions are scoped by folder, so `connectors/slack/tools/add_reaction.ts` extends
the `add_reaction` tool only when the `slack` connector is active. The extension file does not repeat
`connector: "slack"`; the folder name is the connector id. These tools are for real platform
capabilities such as reactions or modals. Presentation-only web/json-render code belongs in `ui/` or
connector renderers, not in model-visible tools.

`ui/` is an optional home for shared web UI types and components. It is useful when multiple web apps
render the same agent-specific tool output parts.

## CLI

```bash
npx @little-stack/harness@alpha init # guided workspace wizard
little-harness init --here    # scaffold into the current directory
little-harness new support    # add agents/support/ to an existing workspace
little-harness test support   # load the agent and chat with it interactively (REPL)
little-harness dev support    # serve it, restart on change, chat in the terminal
little-harness start support  # serve it: connectors, an HTTP API, schedules
```

`test` opens an interactive REPL: type a message, the agent streams its reply, and the conversation
persists across turns. Assistant text, reasoning, tool calls, and tool results are printed as labeled
blocks, with tool input and output payloads shown when available. Type `:reset` to clear the
conversation or `:exit` to quit.

## Loading from code

You can load an agent folder yourself (the CLI uses these under the hood):

```ts
import { loadHarness, loadWorkspace } from "@little-stack/harness";

const { agents } = await loadWorkspace();          // enumerate agents/*
const harness = await loadHarness("agents/support"); // a runnable Harness with tools, skills, and workflows merged
```

To run a folder's agent on a different host than the one its `agent.ts` configures — for example a
throwaway data directory in a test or a script — pass `host`. The loaded harness then takes its
sessions from that host:

```ts
import { loadHarness, localHost } from "@little-stack/harness";

const harness = await loadHarness("agents/support", {
  host: localHost({ dataDir: ".little-harness-test" }),
});
```

## Build agent folders for workerd

**Ships in `0.2.0-alpha.3`:** `@little-stack/harness/compiler`, `/compiled`, and host-factory
agent exports.

`loadHarness()` uses Node filesystem discovery and a TypeScript module loader.
For workerd, compile the folders on your build machine and bundle the generated
static imports with your worker. The standalone `demos/workerd-folders` example
runs two agent folders without LittleDB or a model key.

```ts
// Build script, running in Node. Write this TypeScript module in moduleDir.
import { writeFile } from "node:fs/promises";
import { compileHarnessWorkspace } from "@little-stack/harness/compiler";

await writeFile("src/agents.generated.ts", await compileHarnessWorkspace(".", {
  moduleDir: "src",
}));
```

For a single folder, `compileHarnessFolder("agents/support", { moduleDir: "src" })`
returns a module whose default export is an async factory accepting `{ host }`.
For a workspace, the generated module exports `agents` and
`loadHarness(name, { host })`. Both require the application's per-chat host:

```ts
import { virtualHost } from "@little-stack/harness";
import { loadHarness } from "./agents.generated.js";

// Once per chat / Durable Object, using that chat's filesystem.
const host = virtualHost({ fs: chatFiles });
const harness = await loadHarness("support", { host });
```

For chat-local tool closures, default-export a factory from `agent.ts`:

```ts
import { createHarness, type HarnessHost } from "@little-stack/harness";
export default (host: HarnessHost) => createHarness({ host, model });
```

The Node loader also accepts this form with `loadHarness(folder, { host })`. Without a host, Node shares a fallback `localHost()` per resolved data directory in the process, including its session queue and concurrency limit; CLI/server callers pass their selected data directory. Explicit hosts bypass this cache. Existing Harness object exports retain their own host unless explicitly overridden.
The fallback host cache is never cleared and uses `resolve()`d paths rather than `realpath()`, so applications loading many data directories or accessing one through symlinked paths should pass an explicit `host`.
Keep imported tools stateless; module-level state is shared, while factory-local
state belongs to that invocation. Existing default-exported Harnesses remain
supported, with both `config.host` and `sessions` overridden by the supplied host.

The compiled path shares Node's merge and workflow/name validation rules. It embeds
`instructions.md` and bare `skills/<name>/SKILL.md` folders with nested binary or
text assets. `skill.ts` takes precedence and must export inline
`{ name, description, files }`, as must configured skills. Disk/Git skill inputs
fail clearly instead of trying to load Node files or fetch Git at runtime.
Symlinks, special skill files and skills over 2 MB fail the build; set
`maxSkillBytes` to adjust the limit. Every regular file in a bare skill folder is
bundled, so include only intended assets there.

The compiler returns source without executing authored modules. Your bundler and
runtime still process trusted imports; this is not a sandbox. Rebuild after folder
changes, enable `allowImportingTsExtensions` with `noEmit` for generated-source
typechecking, and keep Node-only modules out of your worker. Scheduling, connectors,
chat routing, storage, authentication and network policy remain application-owned.
